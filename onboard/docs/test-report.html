1The philosophy

The shape of a test suite should follow from where the bugs actually are, not from a diagram someone drew in 2009.

onboard is a small server-rendered app: a Superadmin manages Leaders, Leaders invite Members by email, Members tick three onboarding checkboxes. Roughly all of its code is glue — HTTP in, a SQL statement, an HTML template out. There is almost no algorithm to speak of.

That single observation determines everything below. Two questions decide a strategy:

  1. Where do the bugs actually come from? In this codebase: the seams. Foreign keys that cascade in a cycle, a form field that arrives as an array instead of a string, a cookie whose expiry is computed from the wrong clock. Not one of those is visible inside a single function.
  2. What does a failing test need to tell you? Enough to find the fault without a debugger. "The element never appeared" is a poor answer; "POST /team/invites returned 500" is a good one.

Weighting the middle answers both. Each integration test exercises real HTTP against real Postgres — so nothing can hide behind a mock — while still naming a route and a status code when it fails.

The three classic strategies, and why this one

StrategyShapeBest atBlind toFit here
Pyramid Mostly unit Dense algorithmic logic; instant feedback; pinpoint failures Everything between units — with a mocked query(), every bug this app actually had would still be green Poor
E2E-only Browser journeys Real user-visible confidence; survives any refactor Edge cases, on cost grounds — and failures point at the wrong layer Partial
Trophy chosen Mostly integration Component seams — where glue code breaks Deep algorithmic corners (there are none here) Good
Historical footnote

The pyramid's original argument was economic: in 2009, end-to-end tests were slow, flaky and Selenium-driven. Playwright's auto-waiting and throwaway containerised databases changed that cost by an order of magnitude. Advice inherited from the pyramid era is often solving a problem you no longer have — but note the pyramid is still right for a compiler or a pricing engine. The shape follows the codebase.

One rule that outranks the shape

A test you have never seen fail is not evidence. Every non-obvious assertion in this suite was verified by deliberately breaking the code and watching the test go red — see §6. That practice is what caught the one test in this suite that was quietly worthless (§5).

Why 93 and not 5

The same assertion costs about twenty times more through a browser. Verifying that a too-short password is rejected and leaves the invitation still usable takes roughly 20 ms over HTTP and roughly 400 ms through Chromium. That ratio is the entire argument: at HTTP level you can afford ninety-three cases, and at browser level you cannot.

Running them

shell
# everything: unit, then both Playwright projects
npm test

# one layer at a time
npm run test:unit          # 17 · ~0.3s · no infrastructure
npm run test:integration   # 93 · ~12s
npm run test:e2e           # 5  · ~3s

# interactive: pick tests, watch, time-travel
npm run test:ui

pretest brings Postgres up first, so npm test works from cold. Both Playwright projects share one webServer and run on a single worker, because they share one database.

3How a test gets its data

Read this before writing a new test — the fixture mechanics explain most of the surprises.

Named seeds, never ad-hoc setup

A test does not build its world by hand. It names one of six seeds and the database is dropped and rebuilt to exactly that state:

SeedContentsUsed for
baseSuperadmin onlyEmpty-system tests; the production starting point
superadmin-and-leader+ 1 Leader with an empty teamInvitation sending, progress setup
two-leaders-one-with-member2 Leaders, 1 Member, 1 completed stepBasic cascade, dangling sessions
member-two-of-threeOne user of every role, 2 of 3 steps donePersistence, the authorization matrix
leader-with-three-members3 Members with 0 / 1 / 3 steps doneCascade depth
pending-invitation+ 1 unredeemed invitationInvitation acceptance, single-use
Gotcha

POST /__test/reset also clears server-side sessions. Reset first, then log in — resetting mid-test silently logs every client out, and the symptom is a redirect to /login rather than an error. Two tests were written the wrong way round during development and had to be fixed.

Determinism is a hard requirement, not a nicety

The e2e layer compares whole-database snapshots byte for byte, so nothing in the database may vary between runs. Three rules make that hold:

  • One fixed instant. Every timestamp is 2024-01-01T00:00:00Z. Not a counter, not a clock — a counter would differ between "run one test" and "run the suite", because the server process outlives the per-test resets.
  • Content-derived tokens. An invitation token is a hash of (team, email, nth), so a test can compute the link before it exists.
  • Email-derived salts. Password hashes are stable across runs. This is a deliberate MVP shortcut and a real weakness — see §8.

Seven integration tests guard that property directly, so a stray NOW() fails with a clear message instead of surfacing later as a puzzling snapshot diff.

Asserting on the database

GET /__test/dump returns every table and row, ordered by id. Integration tests assert on specific rows; e2e tests additionally compare the full dump against a file in tests/expected/.

Snapshots that cannot cheat

A missing expected file fails the test — it is never written during a normal run. A snapshot helper that records itself on first use passes trivially and proves nothing. Recording is an explicit act (UPDATE_DUMPS=1), and it exits non-zero to force you to read the diff.

Three endpoints exist only when ONBOARD_TEST_SUPPORT=1, which Playwright sets and a normal server does not: /__test/reset, /__test/dump, /__test/emails. The email one reads the fake mail service's outbox, which is how tests get hold of invitation links.

auth.test.js8 tests Password hashing and role routing — the only genuinely algorithmic code in the app.

Hashing is deterministic by design here, which makes it unit-testable. These tests pin the properties that matter and would otherwise be invisible.

  1. hashPassword is deterministic for the same email and password
  2. hashPassword differs for the same password under different emails The whole point of a per-user salt: two users sharing a password must not share a hash.
  3. hashPassword differs for different passwords
  4. hashPassword never stores the password in the clear Cheap, but catches the catastrophic refactor.
  5. verifyPassword accepts the right password and rejects wrong ones Includes case and trailing-space variants.
  6. verifyPassword rejects a hash minted for a different email Proves the salt is actually bound to identity.
  7. homePathFor routes each role to its own landing page
  8. homePathFor sends anonymous visitors to the login page
invitations.test.js5 tests Token derivation: deterministic, well-formed, collision-free.

Tokens are hashes of (team, email, nth) rather than random values, so seeds stay reproducible. That makes correctness a property of a pure function.

  1. inviteToken is deterministic for the same inputs
  2. inviteToken is a 32-character hex string
  3. inviteToken varies with team, email and sequence number All three inputs must matter, or two invitations could collide.
  4. inviteToken collisions are absent across a spread of inputs 100 combinations, 100 distinct tokens.
  5. inviteUrl joins the base URL and token without a double slash
onboarding.test.js4 tests The hardcoded step registry — the contract every other layer assumes.

isStepKey is the guard that stops an arbitrary URL segment from becoming a database row, so its rejection behaviour is worth stating explicitly.

  1. there are exactly three onboarding steps
  2. step keys are unique and non-empty
  3. every step has a human-readable label
  4. isStepKey accepts known keys and rejects everything else Rejects '', wrong case, path traversal, null, undefined.

invitations.spec.js16 tests The invitation lifecycle: sending (7) and accepting (9).

An invitation link is a bearer credential, so this file carries most of the app's security-relevant behaviour.

Sending

  1. an invitation is stored as pending and emailed with a matching link The emailed token must be the one in the database, not a re-derivation that happens to agree.
  2. the invitation token matches the documented derivation
  3. inviting the same address twice while pending is rejected
  4. inviting someone who already has an account is rejected
  5. an empty email address is rejected
  6. the invited address is lowercased and trimmed
  7. two different invitations produce two emails and two rows

Accepting

  1. the accept page names the invited address
  2. accepting creates a member on the inviting leader's team
  3. accepting logs the new member straight in
  4. the account email comes from the invitation, not the request body Security: someone holding a link must not be able to choose their own address, role or team. Posts email, role and team_id and asserts all three are ignored.
  5. a short password is refused and leaves the invitation usable Validation runs before the claim, so a rejected attempt must not burn the invitation. Then re-uses the link successfully to prove it.
  6. an unknown token is refused
  7. a used token is refused with a distinct message
  8. posting to a used token does not create a second account
  9. two simultaneous redemptions create exactly one member Asserts the user-visible invariant only — see §5 for why this test cannot prove atomicity.
auth.spec.js13 tests Login, session lifecycle, and the two ways a session can outlive its own validity.
  1. the login page is reachable without a session
  2. each role is redirected to its own landing page
  3. a session cookie is issued with a relative lifetime Asserts Max-Age, not Expires. An absolute expiry built from the fixed 2024 test clock would already be in the past and the browser would silently drop the cookie.
  4. the wrong password is refused 401, and no cookie issued.
  5. an unknown email is refused with the same message as a wrong password No user enumeration. Compares the rendered error text, not the whole body — the form legitimately echoes back the submitted address.
  6. an empty password is refused

  8. surrounding whitespace in the email is ignored
  9. the root path routes by role

  12. a session whose user was cascade-deleted is logged out, not served an error Deleting a Leader removes their Members. A live session then points at a row that no longer exists — the classic 500. Asserts a redirect instead.
  13. an unknown path renders a 404 page
onboarding.spec.js13 tests Checkbox writes: idempotency, deletion, attribution, and what the Leader sees.

This file builds its Member through the real invitation flow rather than a seed, so it never depends on pre-existing progress rows.

  1. a fresh member starts with no progress rows
  2. checking a step writes exactly one row
  3. checking all three steps writes three rows and reports completion
  4. re-checking an already-checked step is idempotent Asserts the original row id is unchanged — ON CONFLICT DO NOTHING, not a replace.
  5. a double-submitted step still yields one row Two concurrent writes, as a double-click produces.
  6. unchecking a step deletes its row
  7. unchecking a step that was never checked is harmless
  8. re-checking after unchecking creates a new row Documents that the id advances — a detail the snapshots would otherwise pin silently.
  9. unchecking one step leaves the others alone
  10. an unknown step key is rejected and writes nothing 404 for nope, wrong case, and a traversal attempt.
  11. progress is attributed to the session user, not to request input Security: posts a forged user_id and asserts it is ignored.
  12. the leader sees the member progress count update
  13. a leader does not see members of another team Tenant isolation.
leaders.spec.js11 tests Superadmin CRUD, and the three things the delete route must refuse.
  1. creating a leader also creates exactly one team for them And the Leader's own team_id stays null — they own a team without being in one.
  2. the new leader can log in with the password that was set Closes the loop between creation and authentication.
  3. a duplicate email is rejected and creates nothing
  4. the superadmin email cannot be reused for a leader
  5. a missing email or password is rejected Three variants; nothing created.
  6. the email is stored lowercased and trimmed
  7. the leader list shows each leader and their member count
  8. removing a leader deletes them and their team
  9. removing a non-existent leader is a harmless no-op

cascade.spec.js8 tests The trickiest thing in the schema: a delete that unwinds a foreign-key cycle.

users.team_id and teams.leader_id reference each other. A single DELETE FROM users therefore has to unwind two tables in a cycle plus two dependents. The documented decision is that everything cascades — team, Members, their progress, the team's invitations — with nothing left as an orphan.

The fixture deliberately mixes 0, 1 and 3 completed steps across three Members.

  1. the fixture starts in the expected shape 6 users, 2 teams, 3 invitations, 4 progress rows — so a later failure cannot be blamed on setup.
  2. a leader with three members takes their whole team with them
  3. progress rows disappear regardless of how far along the member was
  4. the other leader's team is untouched The cascade must be bounded.
  5. deleting the childless leader leaves the populated team intact
  6. deleting both leaders empties everything but the superadmin
  7. a deleted leader can no longer log in
  8. a member of a deleted team can no longer log in The cascade must have real authentication consequences, not just missing rows.
determinism.spec.js7 tests Guards the property the entire snapshot approach rests on.

Without these, a stray NOW() or random() would surface as a confusing snapshot diff in some unrelated e2e test. Here it fails by name.

  1. every seed produces an identical dump when applied twice All six seeds, reset twice, compared.
  2. no seeded timestamp comes from the real clock Asserts the current year appears nowhere in any dump.
  3. rows created through the app also use the fixed clock Not just seeds — live writes too.
  4. an invitation token is reproducible across resets
  5. the dump covers every table and orders rows by id
  6. the base seed contains only the superadmin The spec's stated starting state.
  7. resetting truncates data left by a previous test Test isolation itself, asserted.
invitation-claim.spec.js3 tests Atomicity of the single-use claim, tested with two hand-interleaved transactions.

The only file that talks to Postgres directly instead of over HTTP. It exists because the HTTP-level version of this test cannot prove what it appears to. Read §5 — it is the most instructive thing in this suite.

  1. two interleaved transactions cannot both claim one invitation Deterministic via Postgres row locking. Fails when the AND status = 'pending' predicate is removed — verified.
  2. claiming an already-accepted invitation returns nothing
  3. claiming a non-existent invitation returns nothing

e2e  5 tests · tests/e2e/

01 … 05 · the five mandated journeys5 tests Real Chromium, real clicks. Each ends with a full-database snapshot comparison.

These were specified before a line of code existed, and they are unchanged by the move to a mixed strategy. Their job is different from the integration layer's: they prove a person can complete a task, including that the HTML renders, the forms submit, and the checkboxes reflect stored state.

  1. 01 — superadmin can create leaders in an empty system Starts from Superadmin-only, creates two Leaders, verifies the database.
  2. 02 — a leader invites a member and sees their progress Two browser contexts. Invites two people, one accepts, ticks boxes one at a time; the Leader's view is re-read after each and must track 0/3 → 3/3.
  3. 03 — a leader with a member is deleted The cascade, through the UI, with the surviving Leader asserted intact.
  4. 04 — onboarding progress is stored in the database Two boxes render checked, tick the third, log out, log back in, all three still checked. Exactly three rows, no duplicates.
  5. 05 — an invite link can only be used once Redeem, then revisit the same link and confirm no second account.
Why these keep their snapshots

An integration test asserts a handful of rows it cares about. These five assert the entire database, which catches damage the author never thought to look for — a stray row, a wrong team_id, an invitation left pending. That is worth the browser cost five times, not ninety-three.

5Case study: a test that lied

The most useful thing in this report. A plausible, well-named, passing test that proved nothing at all.

An invitation link must be single-use. The mechanism is a claim inside a transaction: flip the row to accepted only if it is still pending, then create the Member — both or neither.

src/invitations.js
export async function claimInvitation(client, invitationId) {
  const { rows } = await client.query(
    `UPDATE invitations
        SET status = 'accepted', accepted_at = $2
      WHERE id = $1 AND status = 'pending'   -- ← the whole safety property
      RETURNING *`,
    [invitationId, now()],
  );
  return rows[0] ?? null;
}

The obvious test

Fire two requests at the same link and assert only one account appears:

const [first, second] = await Promise.all([
  post(a, invite(TOKEN), { password: 'race-one-pass' }),
  post(b, invite(TOKEN), { password: 'race-two-pass' }),
]);
expect([first.status(), second.status()].sort()).toEqual([302, 410]);

It passes. It reads well. It is worthless.

Measured, not assumed

Delete AND status = 'pending' — removing the entire safety property — and this test still passes. So does the sequential replay test next to it. Ten genuinely parallel requests behave identically: one 302 and nine 410s, one Member created, all green.

Why it cannot work

The window between reading the invitation and committing the claim is well under a millisecond. Two HTTP requests cannot be delivered close enough together to land inside it — the second arrives after the first has committed, and is turned away by the handler's cheap pre-check (status !== 'pending') long before the claim is reached. The test never exercises the code it was written for. It exercises the pre-check, twice.

This is the general failure mode: a test can pass by a path that has nothing to do with the property it names. Concurrency is where it bites hardest, because the race you are trying to provoke is precisely the thing you cannot schedule from outside.

The fix

Stop trying to race over HTTP. Extract the claim into its own function, then drive two transactions from the test and interleave them by hand. Postgres row locking makes the ordering deterministic rather than lucky:

tests/integration/invitation-claim.spec.js
await first.query('BEGIN');
await second.query('BEGIN');

// The first transaction claims the row and holds its lock.
const claimed = await claimInvitation(first, id);
expect(claimed).not.toBeNull();

// The second now blocks on that lock. Do not await it yet.
const contender = claimInvitation(second, id);

await first.query('COMMIT');

// Released, the second re-evaluates `status = 'pending'` against the
// committed value, matches nothing, and comes back empty.
expect(await contender).toBeNull();
This one fails when it should

Remove the predicate and 2 of these 3 tests go red immediately. That is the difference between a test and a decoration.

Three transferable lessons

  • A test you have never seen fail is not evidence. Break the code on purpose. If nothing goes red, you have written documentation, not a test.
  • Ask which path made it pass. Green because the property holds, or green because a cheaper guard short-circuited first? For concurrency, assume the latter until proven otherwise.
  • Testability is a design constraint. The claim moved out of the route handler because that was the only way to test it honestly. The refactor improved the code as a side effect.

The HTTP-level test was kept — it does assert something real, namely the user-visible invariant that one client is admitted and the other refused. Its comment now says exactly that, and points here for the atomicity.

6Proof the suite bites

Every non-obvious guarantee below was checked by breaking the code and confirming the right tests went red.

Deliberate breakExpected to failResult
Delete AND status = 'pending' from the claim The atomicity tests 2 of 3 failed ✓
Same break, judged by the HTTP race test only Nothing — documented blind spot Passed ✗ — see §5
Widen requireRole('member') to accept every role 4 matrix tests (2 routes × 2 wrong roles) Exactly 4 failed ✓
Change leader_id in an expected e2e snapshot The snapshot comparison Failed with a clear diff ✓
Delete an expected snapshot file The test, rather than silently re-recording All 5 failed ✓

The second row is deliberately kept in this table. A suite's blind spots are worth recording as explicitly as its guarantees — an undocumented blind spot reads as coverage.

Also verified

The full suite was run twice back to back with identical results (115 passing, ~16 s), which is what proves the snapshot comparisons are real rather than self-recording, and that no test leaks state into the next.

7Where to put a new test

The layer boundaries are the whole value of this structure. Keeping them sharp is a maintenance task.

If you are testing…LayerBecause
A function that takes values and returns valuesunitNo infrastructure needed; failures name the function
A route's status, redirect, or the rows it writesintegrationReal DB and HTTP without the browser tax
An access-control ruleintegrationAdd a row to the matrix table; the tests generate themselves
SQL semantics — locking, cascades, constraintsintegrationOnly a real Postgres can answer; talk to it directly if needed
Rendered HTML that a human must read or clicke2eOnly a browser proves it renders and submits
A multi-step task a real user performse2eJourneys are what this layer is for — but keep it to five-ish

House rules

  1. Reset first, log in second. /__test/reset clears sessions, so any client authenticated beforehand is silently anonymous afterwards.
  2. Name a seed; never hand-build state. If no seed fits, add one to src/seed.js with explicit ids and the fixed clock. Deterministic dumps are non-negotiable.
  3. Never introduce randomness or a real clock into anything that reaches the database. Seven tests will catch you, which is the point.
  4. Assert the negative too. "The request was rejected" is half a test; "and nothing was written" is the other half. Several tests here re-use a resource afterwards to prove it survived.
  5. Then break the code and watch it fail. If your new test stays green, find out which path made it pass before you commit it.

8Deliberate gaps

What is knowingly untested, and why. An unstated gap is worse than a known one.

Not covered, by choice

  • Visual regression. The CSS carries no requirements; screenshot diffs would be brittle noise.
  • Load and performance. No requirement exists to violate.
  • Accessibility. Worth adding if this grows past an MVP; not specified here.
  • Browsers other than Chromium. The pages are plain server-rendered HTML with one inline onchange; cross-browser risk is close to nil.
  • Atomicity under real HTTP concurrency. Structurally impossible from outside the process, and documented as such in §5 rather than papered over.

Known weaknesses in the code itself

Password salts are derived from the email

Not random — so that seeded password hashes stay stable in the byte-comparable dumps. The consequence is that two users with the same password have the same hash, which a random salt exists to prevent. Before production: switch to a random salt and redact password_hash from the dump. Flagged in src/auth.js and the README.

Sessions live in process memory

Fine for one process; a restart logs everyone out and it will not survive being scaled to two instances. The suite tests the behaviour that exists, including server-side invalidation on logout and dangling sessions after a cascade delete.

An invitation link is a bearer credential

Anyone holding it can create the account. That is the design — an emailed link is the only proof of address the system has. It is bounded by tests: the address, role and team all come from the invitation and never from the request body, and the link works exactly once.
